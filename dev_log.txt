📘 GPU Image Pipeline — Dev Log (Day 4)

Date: 30-01-2026
Focus: CUDA architecture correction, compilation model clarity, GPU context design, and real performance gains

1. Context

Today’s work was not about adding a new algorithm.
It was about fixing architecture and understanding why CUDA code behaves the way it does.

I already had:

a working CPU grayscale

a working GPU grayscale

correct output (0 mismatches)

But GPU performance was worse than CPU, which felt wrong.

The goal for today became:

Understand why — and fix it the right way.

2. Major Conceptual Breakthrough: CUDA Compilation Model

Learned and internalized the true separation of concerns in CUDA projects:

Headers (.hpp)

Declarations only

Provide knowledge to the compiler

Do not connect files or implementations

Source files (.cpp, .cu)

Implementations

Compiled as separate translation units

Connected only at link time, not by #include

Critical rule learned:

Headers do not connect .cpp and .cu files.
CMake + the linker do.

This clarified:

why grayscale_kernel.hpp exists

why .cu files don’t need to include their own headers

why including .cu files is wrong and dangerous

3. File Extension Rule (Very Important)

Hit (and understood) a classic CUDA error:

expected primary-expression before ‘<’ token


Root cause:

Kernel launch syntax <<< >>> is not C++

Any file that launches a kernel must be compiled by NVCC

New rule locked in:

If a file contains <<< >>>, it must be a .cu file.

This led to:

Renaming grayscale_gpu.cpp → grayscale_gpu.cu

Clean separation between:

host orchestration

device kernels

4. Architectural Refactor: GPU Context Design

Introduced a GPU context struct to manage device memory lifetime:

struct GrayscaleGPUContext {
    uint8_t* d_input;
    uint8_t* d_output;
    int width;
    int height;
};

Designed three explicit lifecycle functions:

grayscale_gpu_init → allocate device memory (once)

grayscale_gpu_run → memcpy + kernel launch (hot path)

grayscale_gpu_destroy → free device memory (once)

Key insight:

Allocating or freeing GPU memory inside the hot path destroys performance.

This mirrors good systems design:

ownership is explicit

lifetime is controlled

execution stays lean

5. Kernel Isolation

Refactored GPU code into clean layers:

grayscale_kernel.cu

device-only code

no allocations

no host logic

pure computation

grayscale_gpu.cu

host-side CUDA logic

kernel launch

memcpy

synchronization

This eliminated:

duplicated allocations

unclear ownership

“do-everything” CUDA files

6. CMake Understanding & Fixes

Clarified multiple CMake concepts:

Difference between:

cmake ..

cmake -S . -B build

Why both work on Ubuntu

Why explicit -S/-B is safer and more scalable

Ensured CMake:

treats .cu files as CUDA

uses NVCC where required

links OpenCV and CUDA runtime correctly

compiles kernels in separate translation units

Final result: clean build, no hacks.

7. The Performance Moment (Payoff)
Before refactor (alloc + copy + kernel + free every run):
GPU Grayscale time: ~132 ms

After refactor (allocation once, lean hot path):
GPU Grayscale time: ~3.4 ms
CPU Grayscale time: ~27 ms
Total mismatched pixels: 0


Same kernel.
Same math.
Same image.

Only architecture changed.

Core realization:

The GPU was never slow.
The design was.

This was the clearest demonstration so far that:

CUDA performance is dominated by lifetime management

“working CUDA” ≠ “correct CUDA”

8. Key Takeaways (Locked In)

CUDA is not just about kernels — it’s about systems design

Headers are contracts, not connectors

.cu vs .cpp is not cosmetic — it defines the compiler

GPU memory allocation must never be in the hot path

Meaningful benchmarking requires correct architecture first

📘 GPU Image Pipeline — Dev Log (Day 5)

Date: 31-01-2026
Focus: Gaussian Blur — concepts, memory hierarchy, and kernel design (no premature coding)

1. Context & Intent

Today’s goal was explicitly not to rush into CUDA code.

Instead, the focus was to:

deeply understand Gaussian blur as a computation

understand why shared memory is required

design the kernel architecture before touching syntax

This marked a shift from “writing CUDA” to designing GPU algorithms.

2. Why Gaussian Blur Is the Right Next Step

Identified Gaussian blur as the first non-embarrassingly parallel operation in the pipeline.

Key realization:

Each output pixel depends on neighboring input pixels

Threads do not depend on each other’s results, but they reuse the same input data

This introduces data reuse, not data dependency

This makes Gaussian blur the canonical example for learning:

shared memory

tiling

halo regions

synchronization

3. Shared Memory & Tiling — Conceptual Breakthrough

Worked through the naïve implementation and identified the true bottleneck:

redundant global memory loads

not arithmetic

Designed a tiled approach:

Block size: 16×16 output pixels

Kernel size: 3×3

Radius: 1

Shared memory tile: 18×18

Derived this using the rule:

shared_tile = block_size + 2 × radius

Confirmed:

256 output pixels

324 shared memory pixels

68 halo pixels loaded cooperatively per block

This was derived mathematically, not guessed.

4. Halo Ownership & Load Strategy

Chose a border-thread loading strategy:

Interior threads load exactly one pixel

Border threads load extra halo pixels

Corner threads load corner halo pixels

Rationale:

optimize for the common case

minimize unnecessary work

keep load phase structured and readable

This introduced the idea of asymmetric per-thread responsibility, a key GPU design concept.

5. Boundary Handling Decision: Mirror Padding

Chose mirror padding as the boundary strategy.

Reasons:

preserves edge continuity

avoids artificial dark borders

matches industry practice (e.g., OpenCV)

forces correct index reasoning early

Derived and understood mirror index mapping:

v < 0 → -v

v >= limit → 2*limit - v - 2

Key insight:

mirror logic belongs in the load phase

convolution phase should be branch-free and uniform

6. Gaussian Kernel Weights — Demystified

Understood why the 3×3 Gaussian kernel uses:

1 2 1
2 4 2
1 2 1


Key takeaways:

discrete approximation of a 2D Gaussian

center pixel weighted most

normalized by sum = 16

derived from Pascal’s triangle

separable, enabling future optimization

Extended intuition naturally to 5×5 kernels, recognizing the Pascal pattern without memorization.

7. Full Kernel Designed in Pseudocode (Major Milestone)

Before writing any CUDA code, designed the entire kernel in structured pseudocode, covering:

Thread & global index calculation

Mapping to shared memory with halo offset

Cooperative loading of:

central pixels

edge halos

corner halos

Mandatory synchronization

Branch-free Gaussian convolution

Single global write per thread

At this point, the kernel logic was fully clear and implementation-ready.

8. Meta-Learning: How CUDA Should Be Learned

Reinforced a critical learning philosophy:

If the idea is clear, the code becomes boring — and that’s a good thing.

Today emphasized:

thinking in blocks, not threads

designing for memory hierarchy

separating what from how

refusing to hide complexity inside syntax

9. Current State

✅ Gaussian blur fully understood conceptually
✅ Shared memory tiling & halo logic designed
✅ Mirror padding math internalized
✅ Kernel written line by line
✅ Ready to wire into code and main pipeline

10. Next Steps

Integrate Gaussian blur into pipeline

Add menu-based dispatcher in main.cpp

Compare grayscale vs Gaussian performance

Key Takeaway (for myself)

Today wasn’t about writing CUDA.
It was about learning how GPUs want you to think.
